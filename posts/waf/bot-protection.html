WAF Bot 防护体系设计：构建分层协同的自动化流量防线

引言

互联网流量中，自动化程序（Bot）的占比持续攀升。除了搜索引擎等良性爬虫，恶意爬虫、漏洞扫描器、撞库工具、CC 攻击脚本等恶意自动化流量，正在消耗服务器资源、窃取内容数据、探测攻击面。传统的 WAF Bot 防护往往以"单点插件"的形态存在：一个插件管频率、一个插件管挑战、一个插件管爬虫白名单，各自独立判断、独立处置，缺乏协同。这种架构存在几个典型问题：

  • 重复判断：每个插件各自做加白、加黑判断，逻辑分散且容易冲突
  • 无记忆能力：防护决策只看当前请求，客户端"这次被挑战、下次换 IP 再来"就能绕过
  • 处置单一：频率超限就封禁、命中就拦截，缺乏递进式的柔性处置手段
  • 误伤合法流量：搜索引擎爬虫被挑战页面挡住，影响站点 SEO

本文介绍一种分层协同的 WAF Bot 防护体系设计，核心思路是六个转变：

  1. 统一入口决策：引入访问策略路由，集中管理加白、加黑与模块调度，各防护模块不再独立承担这些职责
  2. 风险量化驱动：引入风险评估模块，实时评分与行为评分叠加，用统一的"风险分"驱动处置决策
  3. 合法爬虫身份认定独立成层：通过 rDNS 离线验证的 IP 白名单认定合法爬虫，跳过挑战与风险评估，但仍受频率约束
  4. 离线行为分析联动：离线行为分析层消费访问日志，跨请求聚合分析后产出评分和处置结论，实时防护层直接读取执行——实现跨请求的"记忆"能力
  5. 自动化工具指纹库：高置信度的恶意自动化工具的 TLS 指纹与浏览器指纹长期入库，命中即封禁，对方换 IP 也能持续识别
  6. 频率控制递进惩罚：同一客户端多次触发时惩罚等级逐步加重（PoW → 验证码 → 拦截 → 封禁），替代静态单一动作

1. 整体请求处理流程

请求进入
  │
  ▼
访问策略路由
  ├── Step 1: 检查 [all] 加白规则 → 命中则直接放行，终止后续所有处理
  ├── Step 2: 检查加黑规则 → 命中则直接拦截（403），终止后续所有处理
  └── Step 3: 检查部分模块加白规则，输出需要执行的防护模块列表（剔除被豁免的模块）
  │
  ▼
合法爬虫白名单（已验证 IP 白名单匹配，rDNS 离线验证）
  ├── 命中 → 跳过风险评估 + 关键页面防护，直接进入频率控制和自定义规则
  └── 未命中 → 继续完整防护流程
  │
  ▼
防护模块顺序执行（仅执行 Step 3 输出的列表）
  ├── 风险评估模块
  │     ├── 检查行为分析直接处置结论 → 命中则执行对应动作，终止后续
  │     └── 实时评分 + 行为评分叠加 → 超过阈值则触发挑战，终止后续
  ├── 关键页面防护模块
  ├── 频率访问控制模块
  └── 自定义规则模块

整个流程的设计要点：前置的决策都是低成本的内存匹配（白名单、黑名单、爬虫 IP 库），高成本的检测后置（挑战、评分计算），保证正常流量的处理开销最小。

2. 访问策略路由：统一的入口决策点

2.1 职责

访问策略路由是请求的入口决策点，本身不执行防护逻辑，只做三件事：

  • 加白规则的统一判断与放行
  • 加黑规则的统一判断与拦截
  • 输出当前请求需要执行的防护模块列表

2.2 加白规则

加白规则是三元组：(维度, 值, 作用模块列表)。

支持的维度：

维度示例说明
IP / CIDR10.0.0.0/8内网 IP、已知合法出口
业务 Cookie会话标识源站 session cookie
WAF 验证 Cookie签名令牌已通过挑战验证的浏览器会话
API TokenBearer xyz已知合法 API 调用方
TLS 指纹（JA3/JA4）指纹哈希已知合法客户端工具

也支持上述维度的组合，如 IP + TLS 指纹。

语义规则：

  • 单条规则内部的多个维度为 AND 关系：所有维度同时命中该规则才生效（如 IP + TLS 指纹组合，防止单一维度被伪造后绕过）
  • 多条规则之间为 OR 关系：命中任意一条规则即按该规则的作用模块列表生效
  • 作用模块列表为 [all] 时直接放行，跳过后续所有处理（含加黑检查）
  • 作用模块列表为具体模块时，仅将这些模块从本次请求的执行列表中剔除，其余模块正常执行
  • 高价值豁免强制多因素：豁免风险评估、关键页面防护等核心模块的规则，必须配置至少两个维度的组合，禁止单维度（尤其是单 IP 或单 Cookie）豁免核心模块
  • 加白优先级最高，高于加黑规则、行为分析结论和评分，保证"加了白就一定放行"的语义

2.3 加黑规则

加黑规则结构：(维度, 值, 有效期)，维度与加白规则相同。

  • 存储：写入带 TTL 的黑名单存储。来源包括各防护模块的封禁动作（频率递进、自定义规则、关键页面检测失败、行为分析直接处置）及运营手动加黑
  • 生效：命中即在访问策略路由阶段直接返回 403，不进入后续防护流程
  • 冲突裁决：与加白规则同时命中时，仅 [all] 加白可覆盖加黑；部分模块豁免不影响加黑生效

2.4 模块执行列表

访问策略路由的最终输出是当前请求需要执行的防护模块列表：默认包含全部已启用模块，命中部分模块加白规则时将对应模块剔除。后续防护模块严格按列表顺序执行，未在列表中的模块不执行。

3. 风险评估模块：实时评分与行为评分叠加

3.1 职责

风险评估模块作为防护流程中的第一个执行项，回答"这个客户端当前的风险级别是什么"，结论直接驱动后续动作。

  • 输入：客户端标识（IP、TLS 指纹、Cookie 等）
  • 输出：{ action: block / challenge / observe / pass, score: N }

3.2 行为分析直接处置结论（最高优先级）

离线行为分析层对高置信度情况直接输出处置结论（不经过评分叠加），风险评估模块优先检查：

结论类型来源场景输出动作
封禁（含有效期）IP 多次命中蜜罐、爬虫集群成员block，直接 403
强制挑战评分中等但行为可疑challenge，触发挑战
高度观察弱信号积累observe，提升评分基础分，进入后续流程

有直接处置结论时，跳过评分叠加步骤，直接返回结论——高置信度结论不被实时评分稀释。

3.3 评分叠加机制

实时评分：基于单次请求的多层信号（TCP 指纹、TLS 指纹、HTTP Header 特征、UA 交叉验证等），每次请求实时计算，反映当前请求的可疑程度。

行为评分：由离线行为分析层异步写入，反映该客户端标识的历史累计风险。

叠加方式：

最终评分 = 行为评分（基础分）+ 实时评分（增量分）

评分映射到处置动作（阈值为可配置项，此处为默认值）：

最终评分区间处置动作
0 ~ 30放行，进入后续防护流程
31 ~ 60触发挑战（PoW）
61 ~ 80触发挑战（验证码）
81 ~ 95直接拦截（403）
96 ~ 100封禁一段时间

行为评分衰减：行为评分带有效期，到期后基础分回零；不同风险等级对应不同的有效期，高风险的有效期更长。

3.4 挑战闭环

触发挑战后必须保证闭环，避免"通过挑战后下一个请求又被挑战"：

  • 挑战通过：清零该客户端的实时评分，写入签名加白 Cookie；挑战通过事件记录到访问日志，行为分析层消费后下调其行为评分
  • 挑战失败或超时：实时评分保留并累加，计入频率递进的触发次数，同时写入攻击日志——挑战失败是自动化工具的高置信度证据，行为分析层据此将其指纹写入指纹库（见 §8）

3.5 非浏览器请求分支

评分超阈值但请求被明确识别为非浏览器（无 TLS 浏览器指纹、无 Sec-Fetch 头等）时，不下发无法执行的 JS 挑战：

非浏览器类型处置
有鉴权头的 API 请求不降维挑战，按评分映射执行 observe 或拦截
无鉴权请求中低分返回 429 + Retry-After；高分直接 403 或封禁

3.6 封禁粒度

评分达到封禁区间时，封禁 key 为 IP + TLS 指纹组合（无法获取 TLS 指纹时退化为 IP），写入访问策略路由的加黑规则，封禁时长为可配置项。

4. 关键页面防护模块

4.1 功能描述

针对配置的指定 URL（登录页、注册页、短信接口、秒杀接口等高价值目标）设置挑战，如验证码挑战、滑块挑战、机器人检测等。

  • 检测通过：写入签名加白 Cookie，有效期内后续请求携带此 Cookie 跳过挑战；同时清零实时评分
  • 检测失败：写入加黑规则，加黑期间直接拦截

4.2 触发条件

  • 请求 URL 命中配置的挑战 URL 列表
  • 请求不携带有效的加白 Cookie
  • 访问策略路由未加白当前客户端

4.3 非浏览器请求处理

命中挑战 URL 但明确识别为非浏览器请求时，不下发 JS 挑战，转为频率控制逻辑：

非浏览器类型处置
有鉴权头的 API 请求放行，纳入正常频率统计
无鉴权头且公开接口IP + TLS 指纹频率统计，超限返回 429 + Retry-After
无鉴权头且需鉴权接口直接拦截

4.4 加白 Cookie 防伪设计

Cookie 值 = 客户端标识摘要 + 有效期 + HMAC 签名（服务端密钥），并绑定签发时的 TLS 指纹与 UA。校验时签名不符、已过期或客户端特征漂移均视为无效，防止伪造与转借。

5. 频率访问控制模块：递进惩罚机制

5.1 统计维度

支持按以下维度或组合进行频率统计：

客户端类型推荐统计 key
浏览器业务 Cookie；或 IP + WAF 验证 Cookie
非浏览器（有鉴权）API Token
非浏览器（无鉴权）IP + TLS 指纹（JA3/JA4）

统计 key 由配置决定，未配置时按客户端类型自适应选择，支持多维度组合。

5.2 递进惩罚

同一客户端标识的触发次数作为递进依据。用户不配置时使用自适应递进，配置后按配置执行。

默认自适应递进（浏览器）：

触发次数处置动作
第 1 次PoW 挑战
第 2 次验证码挑战
第 3 次403
第 4 次及以上封禁一段时间

默认自适应递进（非浏览器）：

触发次数处置动作
第 1~2 次429 + Retry-After 头
第 3 次及以上封禁一段时间

5.3 状态设计：两类计数器分离

递进机制依赖两类语义不同的计数器，必须分开存储：

  • 频率统计计数：记录当前时间窗口内的访问次数，有效期等于统计时间窗口，窗口结束后自动清零
  • 触发次数计数：记录该客户端已被惩罚的历史次数，有效期较长（如 24 小时），作为递进等级的依据

5.4 与指纹库联动，防止惩罚被"洗白"

触发次数到期清零仅适用于普通客户端。同一客户端在触发次数有效期内达到最高惩罚等级（封禁）后再次触发频率上限的，将该事件写入攻击日志，由行为分析层裁决后将其 TLS 指纹 + 浏览器指纹写入自动化工具指纹库，由长期记忆接管——避免恶意客户端靠"等 TTL 过期"把惩罚等级重置回零。

6. 自定义规则模块

根据请求特征执行用户配置的动作。

6.1 匹配条件

支持对以下请求字段进行条件组合（AND / OR）：

  • URI、Query String、请求方法
  • HTTP Header（指定 Header 名和值）
  • IP / CIDR
  • UA

6.2 执行动作

动作说明
告警写入攻击日志，不拦截
拦截直接返回 403
封禁一段时间写入黑名单，有效期内直接拦截
挑战触发挑战

7. 合法爬虫白名单：基于 rDNS 的身份认定

7.1 定位

合法爬虫白名单是对已知合法搜索引擎爬虫的身份认定机制。谷歌、Bing 等主流搜索引擎会公开其爬虫的 IP 地址段，且均支持 rDNS 反查验证。命中白名单的请求跳过关键页面防护和风险评估，但仍然进入频率访问控制和自定义规则模块——身份合法不等于可以为所欲为。

7.2 识别方式

验证手段说明
rDNS 反查（主验证）对 IP 做反向 DNS 查询，校验域名属于搜索引擎官方域（如 *.googlebot.com、*.search.msn.com），再做正向解析确认指回该 IP。这是搜索引擎官方推荐的验证方式，无法被伪造
IP 地址白名单经 rDNS 验证后的爬虫 IP 段/地址入库，主流程仅做内存匹配；同时支持用户手动添加自定义 IP 白名单
TLS 指纹（JA3/JA4，辅助）各搜索引擎爬虫工具有相对固定的指纹。但 JA3/JA4 伪造门槛低，仅作辅助信号记录，不参与实时认定

关键设计：rDNS 不在请求主流程执行。 DNS 查询延迟不可控，实时反查会拖慢主流程，因此 rDNS 验证全部离线/异步完成：

爬虫类型验证时机主流程行为
已公开 IP 段（Google、Bing 等）白名单更新时验证：定期同步官方 IP 段后做 rDNS 反查确认归属，通过的标记为"已验证"入库仅做 IP 白名单内存匹配，命中即认定
未公开 IP 段（百度等）异步验证：UA 声称是爬虫但 IP 未命中白名单时，将该 IP 投入异步验证队列，rDNS 通过后加入白名单（带有效期）首次请求不阻塞、按常规防护处理；验证通过后后续请求命中白名单
用户自定义 IP录入时验证一次，防止配置错误同已验证白名单

7.3 常见爬虫的验证来源

爬虫验证来源备注
Googlebot官方公开 IP 段 + rDNS（*.googlebot.com）定期自动同步
Bingbot微软公开 IP 段 + rDNS（*.search.msn.com）定期自动同步
BaiduspiderrDNS（*.baidu.com / *.baidu.jp）未公开完整 IP 段，经异步 rDNS 验证入库

7.4 作用范围

模块是否执行说明
风险评估模块跳过已认定为合法身份，无需评分
关键页面防护模块跳过爬虫不能执行 JS 挑战
频率访问控制模块执行合法爬虫也需遵守频率上限
自定义规则模块执行用户可对爬虫配置额外限制或放行规则

7.5 白名单维护

  • 内置白名单：定期从各搜索引擎官方接口自动同步 IP 段，同步后自动执行 rDNS 验证，无需用户配置
  • 异步验证白名单：未公开 IP 段的爬虫经异步 rDNS 验证通过后自动加入，带有效期，过期后需重新验证
  • 用户自定义：支持手动添加额外的 IP 白名单，录入时执行一次 rDNS 验证
  • 局部关闭：用户可对具体站点关闭内置白名单，关闭后爬虫按常规防护处理

8. 自动化工具指纹库：跨请求的长期记忆

8.1 定位

指纹库存储已确认的恶意自动化工具的客户端特征——覆盖恶意爬虫、漏洞扫描器（sqlmap、AWVS、Nessus、dirsearch 等）、渗透利用与撞库工具——供实时层在每次请求时比对。

此类工具的特点是"换 IP 不换 TLS 栈"：攻击者可以轻易切换代理池，但不会轻易重写自己的工具程序，因此 TLS 指纹比 IP 稳定得多。指纹入库后，可在扫描侦察阶段即识别拦截，实现防护前移。

库中仅保存高置信度指纹，命中即封禁；低置信度信号不入库，走行为评分与挑战确认通道。

8.2 入库来源

指纹库仅保存高置信度指纹。实时层（蜜罐、规则引擎）不直接写入指纹库，只写攻击日志；入库统一由行为分析层分析攻击日志后裁决，避免规则误报直接污染指纹库。

来源链路写入内容
行为分析层确认（主入口）消费攻击日志（蜜罐命中、规则命中、挑战失败记录），跨请求聚合后判定为高置信度TLS 指纹 + 浏览器指纹 + IP，长期入库
内置工具指纹（预置）厂商维护的已知扫描器/自动化工具 JA3/JA4 库，经人工验证TLS 指纹 + 默认处置动作，开箱即可识别
人工录入支持安全运营团队手动确认任意维度

8.3 入库维度与有效期

维度有效期说明
TLS 指纹（JA3/JA4）长期（数周~数月）识别同一套工具程序，换 IP 仍有效
浏览器指纹长期（数周~数月）识别同一台设备
IP中期（数小时~1天）作为辅助维度随指纹条目入库，代理池轮换后失效

Session 与纯 IP 的短期封禁由实时层直接执行（写入加黑规则），用于立即止血、覆盖行为分析层的延迟窗口，不经指纹库。

两个重要的边界原则：

  • JA3/JA4 标识的是 TLS 栈而非具体工具。主流浏览器与常见 HTTP 库（如 Chrome、python-requests）的高基数指纹不单独作为入库处置依据，必须与浏览器指纹或 IP 组合，否则会把正常用户一起封掉
  • TCP 指纹和 HTTP Header 特征区分度低，不作为入库标识，仅用于实时评分的辅助信号

8.4 匹配与处置

风险评估模块在每次请求时比对指纹库：

TLS 指纹命中指纹库 → 直接处置（按入库时记录的处置动作）
浏览器指纹命中指纹库 → 直接处置
Session 命中 → 403
IP 命中 → 403

库中指纹均为高置信度，命中即封禁——对确认恶意的自动化工具不下发挑战（它也不会执行挑战），直接拦截，不浪费资源。

8.5 指纹入库的裁决流程

完整链路：

实时层事件（蜜罐命中 / 规则引擎命中 / 挑战失败）
  → 写入攻击日志（同时对当前 Session + IP 短期封禁止血，覆盖分析延迟窗口）
  → 行为分析层消费攻击日志，跨请求聚合分析
      ├── 高置信度 → 写入指纹库（长期），命中即封禁
      └── 低置信度 → 写入行为评分，按评分触发挑战
                        ├── 挑战失败 → 写攻击日志 → 行为分析层确认 → 写入指纹库
                        └── 挑战通过 → 行为评分下调，不入库

高置信度判定示例：

  • 同一 IP 短时间内多次命中蜜罐
  • IP + TLS 指纹组合多次命中蜜罐或攻击规则
  • 同一客户端短时间内大量探测敏感路径（大量 404 / 命中路径字典）→ 目录扫描行为
  • 挑战失败（主动确认：无法完成挑战的客户端即为自动化工具）

低置信度示例（仅提升行为评分，不入库）：单次规则命中、单一弱信号。

9. 可运营性

防护体系必须具备可运营性，否则误报无法收敛：

  • 拦截详情联合原因：每条拦截事件展示触发模块、客户端标识、联合触发原因描述，而不是简单一句"已拦截"
  • 一键加白 / 临时放行：从拦截日志直接操作，写入访问策略路由的加白规则
  • 观察模式：规则命中只记录不拦截，用于新规则试运行
  • 模块开关：每个防护模块可独立关闭，支持逐步排查误报

访问策略路由的加白规则是可运营性的执行载体——运营界面的"一键加白"操作，最终写入的就是访问策略路由的加白规则配置。

10. 模块协同与数据流

访问策略路由
  ├── 读：加白规则配置
  ├── 读：加黑规则（由各防护模块与运营写入）
  └── 写：无（只读决策，不产生副作用）

风险评估模块
  ├── 读：行为分析直接处置结论（行为分析层写入）
  ├── 读：行为评分（行为分析层写入）
  ├── 读：自动化工具指纹库
  ├── 计算：实时评分（多层信号，当场计算）
  └── 写：无（只读计算，不产生副作用）

合法爬虫白名单
  ├── 读：已验证爬虫 IP 白名单（定期同步 + 异步验证补充）
  ├── 读：内置爬虫 TLS 指纹库
  ├── 计算：无（主流程仅内存匹配；rDNS 验证离线完成）
  └── 写：待验证 IP 队列（供异步 rDNS 验证消费）

关键页面防护 / 频率访问控制 / 自定义规则
  ├── 读：访问策略路由输出的模块执行列表
  └── 写：触发计数、封禁状态

行为分析层（离线）
  ├── 读：访问日志
  ├── 读：攻击日志
  └── 写：行为评分、直接处置结论、自动化工具指纹库

自动化工具指纹库（仅高置信度，命中即封禁）
  ├── 写：行为分析层（统一裁决入口）
  ├── 写：预置工具指纹 / 人工录入
  └── 读：风险评估模块（每次请求比对）

性能设计要点：风险评估每次请求需读取处置结论、行为评分、指纹库三类数据。工程实现上应对这三类数据做节点级本地缓存（秒级 TTL），并合并存储访问调用，将单请求的远端存储往返控制在最低限度，避免高 QPS 下共享存储成为瓶颈。

结语

这套体系的核心思想可以概括为三点：

  1. 决策前置、分层过滤：低成本的黑白名单和爬虫认定在最前面拦截大部分确定性流量，高成本的评分和挑战只作用于存疑流量
  2. 实时与离线双轨协同：实时层负责毫秒级判断与立即止血，离线行为分析层负责跨请求聚合与长期记忆，两者通过评分、处置结论和指纹库衔接
  3. 处置柔性递进：从放行、观察、挑战到拦截、封禁，惩罚力度与风险证据匹配，既不错杀正常用户，也不让恶意工具轻易"洗白"重来

Bot 防护不是单一技术点的竞争，而是体系化能力的竞争——谁能把身份认定、风险量化、长期记忆和运营闭环串成一条线，谁就能在对抗中占据主动。
