深入理解 discv4：以太坊节点是如何互相找到的

源码：reth · crates/net/discv4 · 2026-11-07 · Reth 源码阅读

本文基于 reth crates/net/discv4/ 的实现整理，从数据结构、协议报文、交互流程三个层次，把一个陌生节点如何逐步"认识"整张网络讲清楚。

引子：一个孤独节点的冷启动

以太坊是一张去中心化的网络。当一个全新的节点第一次接入时，它对外界几乎一无所知：不知道网络上有哪些节点在线，不知道它们的 IP 和端口，自然也无法和任何人通信。

节点发现协议要解决的，正是这个"冷启动"问题——让一个孤立的节点从零开始，逐步认识网络中的其他成员，并把它们组织成一张可以随时查询的关系表。

reth 中的 net/discv4 就是 Ethereum Discovery v4 协议的实现。用一句话概括它的职责：

通过 UDP 上的 Ping/Pong 报文维护一张 Kademlia 路由表，持续发现新的 peer，顺带探测本机的公网 IP，最终把节点表的变化以 DiscoveryUpdate 事件上报给上层网络模块。

下面我们分三层来拆解它。

第一层：基石——Kademlia 路由表（KBucketsTable）

在讲协议报文之前，必须先理解承载它们的数据结构：KBucketsTable。整张路由表的本质，就是一个保存在堆上的动态数组（Vec）。

内存布局

  • 数组总共有 256 个元素，下标范围 0 ~ 255。
  • 每个元素核心是一个列表：包含 16 个正式槽，外加 1 个候选槽。
    • 正式槽用来存放已经确立关系的节点。
    • 候选槽在节点发现过程中临时存放候选节点。
  • 数组下标不是随意分配的，而是由"该节点与当前节点（自己）之间的距离"计算得来。

距离是怎么算出来的：异或（XOR）

每个节点都有自己的 ID。两个节点之间的距离，就是把它们的 ID 做异或运算：不同的位为 1，相同的位为 0。

异或结果天然表达了"接近程度"：如果两个数的高位相同、只有低位几位不同，异或结果就会很小——这个小值就是它们之间的距离。

从距离到数组下标：log2 向下取整

拿到距离之后，如何确定它落在数组的哪个下标？答案是：

对距离取以 2 为底的对数，再向下取整。

（注意：实际代码用的是位运算，而不是真的调用对数函数。）

举几个例子就能看出规律：

距离范围数组下标
10
2、31
4、5、6、72
8 ~ 153

距离的最大值是 2²⁵⁶ − 1，对它取 log2 得到一个介于 255 和 256 之间的值，向下取整正好是 255。所以：

  • 下标越大，代表距离当前节点越远。
  • 下标 0 的列表虽然有 16 个位置，但实际上最多只能放 1 个节点——也就是离自己最近的那个。
  • 下标 1 最多放 2 个，下标 2 最多放 4 个，依此类推。

这种"近处稀疏、远处稠密"的分布，正是 Kademlia 结构高效查找的关键：它让节点对近距离的邻居有更细的分辨率。

第二层：协议报文——六种 UDP 包

discv4 协议一共定义了六种报文，两两成对：Ping/Pong、FindNode/Neighbors、EnrRequest/EnrResponse。

1. Ping 包

packet-data = [version, from, to, expiration, enr-seq ...]
version = 4
from = [sender-ip, sender-udp-port, sender-tcp-port]
to = [recipient-ip, recipient-udp-port, 0]
  • version：固定取值 4，版本不匹配的包直接丢弃。
  • expiration：UNIX 时间戳，表示过期时间。接收端收到包时要先判断是否过期，过期直接丢弃。
  • enr-seq：一个单调递增的数值。当节点的 IP 地址、UDP 端口号、fork_id 发生变化时，它会递增。此字段可选，填的是自己节点的 enr-seq。

from 和 to 对应的结构体：

pub struct NodeEndpoint {
    /// The IP address of the network endpoint. It can be either IPv4 or IPv6.
    pub address: IpAddr,
    /// The UDP port used for communication in the discovery protocol.
    pub udp_port: u16,
    /// The TCP port used for communication in the `RLPx` protocol.
    pub tcp_port: u16,
}

收到 Ping 后该怎么做？ 应当回复一个 Pong 包。此外，如果对方在过去 12 小时内没有发过任何包，那么在回复 Pong 之后还要再发一个 Ping，重新验证对方。

为什么 Ping 能验证对方？ 通过对方响应的 Pong，我们可以确认两件事：

  1. 发送方的 IP 地址和端口号，与我发出 Ping 时的目标地址一致；
  2. Pong 中记录的 Ping 哈希，与我发出的那个 Ping 的哈希一致。

两者都对上，才能确认对方合法。

2. Pong 包

packet-data = [to, ping-hash, expiration, enr-seq, ...]
to = [recipient-ip, recipient-udp-port, 0]
  • ping-hash：对应 Ping 包的哈希值，用来告诉对方"Ping 的接收者"和"Pong 的发送者"是同一个节点。
  • expiration：同 Ping，过期直接丢弃。
  • enr-seq：与 Ping 中同名字段含义相同，只是这里填的是发送 Pong 的节点的值。

3. FindNode 包

packet-data = [target, expiration, ...]
  • target：目标节点的公钥信息，记为目标节点 A。
  • expiration：过期时间，过期直接丢弃。

收到 FindNode 后需要回复 Neighbors，其中包含距离目标节点 A 最近的 16 个节点。但有个前提：必须先判断发送方是否经过验证，验证通过后才会发出 Neighbors。

pub struct FindNode {
    /// The target node's ID, a 64-byte secp256k1 public key.
    pub id: PeerId,
    /// The expiration timestamp of the packet, an absolute UNIX time stamp.
    pub expire: u64,
}

4. Neighbors 包

packet-data = [nodes, expiration, ...]
nodes = [[ip, udp-port, tcp-port, node-id], ...]
pub struct Neighbours {
    /// The list of nodes containing IP, UDP port, TCP port, and node ID.
    pub nodes: Vec<NodeRecord>,
    /// The expiration timestamp of the packet, an absolute UNIX time stamp.
    pub expire: u64,
}

pub struct NodeRecord {
    /// The Address of a node.
    pub address: IpAddr,
    /// UDP discovery port.
    pub udp_port: u16,
    /// TCP port of the port that accepts connections.
    pub tcp_port: u16,
    /// Public key of the discovery service
    pub id: PeerId,
}

5. EnrRequest 包

packet-data = [expiration]

顾名思义，这个请求就是为了拿到目标节点的 ENR（Ethereum Node Record）信息。一条 ENR 里包含：

  • enr-seq
  • IP 地址、TCP 端口号、UDP 端口号
  • fork-id
  • 公钥信息

这里有几个值得展开的点：

  • IP 地址是公网地址；
  • TCP 端口用于节点之间真正的消息交互；
  • UDP 端口用于节点发现服务；
  • fork-id 是区块链的分叉 ID。当共识规则或状态转换规则发生变化时，会产生硬分叉点——"硬"指的就是不向后兼容。

fork-id 的结构为 ForkId = (R_hash, R_next)：

  • R_hash：从创世块开始，对当前所处分叉点用 CRC32 算法计算出的数值；
  • R_next：下一个分叉点的块号。

如果两个节点的 ForkID 不兼容，它们是无法交互的。

6. EnrResponse 包

packet-data = [request-hash, ENR]
  • request-hash：对应 EnrRequest 包的哈希值；
  • ENR：节点的 ENR 信息。

第三层：动起来——节点发现的完整交互

理解了数据结构和报文，接下来看它们在运行时是怎么串起来的。

自己节点如何触发一次查找（Lookup）

有两条触发路径：

  1. Discv4 实例发送 Discv4Command::Lookup 命令，Discv4Service 执行 self.lookup_with()；
  2. Discv4Service 在 poll 中，如果配置了 enable_lookup，也会周期性调用 self.lookup_with。

lookup_with 做了什么

这是整个发现流程的核心，步骤如下：

  1. 创建一个 LookupContext；
  2. 从 KBuckets 中筛选出符合条件的节点——已验证（最近 12 小时内回复过 Pong）、不处于 find_node 请求中、且距离目标节点最近的 16 个；
  3. 把这 16 个节点存进一个 BTreeMap：key 是距离，value 是 QueryNode。这意味着同一个距离只会保留一个节点。
struct QueryNode {
    record: NodeRecord,
    queried: bool,   // 是否已经发送 find node 包
    responded: bool, // 是否收到 neighbors 包
}
  1. 从 BTreeMap 中找出尚未发送 find node（即 queried == false）的、最近的三个节点；
  2. 如果这一步没找到任何节点，并且整个 Discv4Service 中也没有正在等待响应的 find node，说明当前手上没有任何已验证节点——于是执行 bootstrap，从配置中拿到已知节点，发起验证；
  3. 如果找到了节点，就针对这最多三个节点，逐个检查是否可以发送 find node。

这里有个值得琢磨的问题： 上面筛出来的节点明明已经"已验证、不在途、queried == false"了，为什么不直接发 find node，还要再检查一次能不能发？

因为有一种情况没被前面的条件覆盖：find node 已经发出去了，却迟迟收不到响应，这次 find node 就算失败了。失败的次数会被统计下来，一旦超过设定的阈值，就不再直接发 find node，而是改发 Ping 重新验证对方。

关于 BTreeMap 的一个关键认知： Discv4Service 实例全局只有一个，但每次调用 lookup_with 都会创建新的 LookupContext 和新的 BTreeMap。这是合理的——因为每次查找的目标节点 ID 可能不同，而 BTreeMap 存的是"到目标节点的距离"及其对应节点。

这也顺带说明了一件事：KBuckets 里保存的节点，并不都是围绕自己找到的邻居，也可能是围绕其他目标节点找到的邻居。但无论如何，当一个节点被写进 KBuckets 时，它在动态数组中的下标，永远是按它与自己节点之间的距离计算的。

bootstrap 做了什么

很简单：把配置里的节点放进 kbuckets，然后发送 Ping 包，发送原因是 PingReason::InitialInsert。

收到 Ping 包时

  1. 检查是否过期，过期直接丢弃；
  2. 如果该节点已经在 KBuckets 的正式槽或候选槽里：
    • 2.1 已过期：响应 Pong，再发一个 Ping，原因 PingReason::EstablishBond；
    • 2.2 未过期：更新 KBuckets 中该节点的 enr_seq，响应 Pong，发送 find node；如果已有的 enr_seq 与 Ping 中的不同，或者原本就没有 enr_seq，则继续发送 enr_request；
  3. 如果该节点不在 KBuckets 里，则尝试插入：
    • 3.1 插入成功：响应 Pong，发送 Ping，原因 PingReason::InitialInsert；
    • 3.2 KBuckets 已满：响应 Pong，发送 Ping，原因 PingReason::EstablishBond。注意此时这个节点并没有进 kbuckets。后续对端响应 Pong 时，当前节点只会做一件事：把对方放进 received_pongs 表。只有在 received_pongs 表中的节点，当前节点才会对其响应 neighbors、enr response。

收到 Pong 包时

  1. 检查是否过期，过期直接丢弃；
  2. 检查这是不是自己发出的 Ping 的响应，不是则直接丢弃；
  3. 把对方节点信息放进 received_pongs 表；
  4. 根据当初发送 Ping 的原因分别处理：
    • 4.1 InitialInsert：更新对方在 KBuckets 中的状态、enr_seq 等信息；
    • 4.2 EstablishBond：同上；
    • 4.3 RePing：更新对方的 enr_seq，并根据 enr_seq 是否变化决定是否发送 enr_request；
    • 4.4 Lookup：更新对方在 KBuckets 中的状态、enr_seq，并把该节点放进 pending_lookup。

当前节点会把发送 Pong 的节点放进 KBuckets，并标记为已验证。等到下一次触发 lookup 时，就可能找到这些节点，进而向它们发送 find node。

小结： Ping/Pong 的作用一是保持 kbuckets 中节点的"有效"状态（类似心跳），二是携带 enr_seq 检查——一旦发现 enr_seq 更新了，就会触发 enr_request 的发送。

收到 FindNode 包时

  1. 检查是否过期，过期直接丢弃；
  2. 检查对方是否已验证（是否在 received_pongs 表中）。若在，则从 KBuckets 中找出距离目标节点最近的、最多 16 个节点，把它们的信息发给对方。

收到 Neighbors 包时

  1. 检查是否过期，过期直接丢弃；
  2. 如果不是自己发出的 find node 的响应，直接丢弃；
  3. 一个 find node 请求可能收到多个 Neighbors 包，如果这些包中的节点总数超过 16，直接返回；
  4. 判断包中的节点是否是黑名单节点，是则直接返回；
  5. 把节点加入 BTreeMap；
  6. 从 BTreeMap 中找出最近的、且没有 find node 在途的、最多三个节点：
    • 6.1 如果 KBuckets 中没有这个节点，就插入 KBuckets；插入成功则发送 Ping，原因 PingReason::Lookup；
    • 6.2 如果 KBuckets 中已有这个节点且已验证：向它发送 find node 的失败次数若超过配置的最大值，则改发 Ping（原因 PingReason::Lookup）；否则发送 find node。

查找为什么一定会收敛

Neighbors 会触发新的 find node，find node 的响应 Neighbors 又会触发新的 find node——这个过程什么时候结束？

答案藏在几条规则里：

  • 发送 find node 之后，对应节点会被标记为 queried；下次再处理 Neighbors 时，这个节点不会重复发送 find node；
  • 如果 find node 发出后没收到任何 Neighbors，失败次数 +1（记录在 kbuckets 中），超过阈值后就把该节点从 kbuckets 中删除；
  • 只有在交互过程中持续发现距离目标更近的新节点时，才会不断发送 find node。

而关键在于：节点到目标的距离范围是有限的（0 ~ 255），且同一个距离只保留一个节点。 空间有限、每轮都在向更近处收敛，所以这个过程最终一定会停下来——不再需要发送 find node。

收到 EnrRequest 包时

  1. 判断当前客户端是否支持 eip868 协议，不支持直接丢包；
  2. 检查是否过期，过期直接丢弃；
  3. 检查发送方是否已在 received_pongs 表中——不在就说明没验证过，直接丢包；
  4. 发送 enr response，把自己的 ENR 信息发出去。

收到 EnrResponse 包时

  1. 检查这是不是自己发出的 enr_request 的响应，不是则直接丢包；
  2. 检查带回的 enr_request 哈希值是否正确、公钥信息是否正确，不正确直接丢包；
  3. 取出 enr_response 中的 fork id，更新 kbuckets 中对应节点的 fork_id。

结语

回头看，discv4 的设计其实非常克制：

  • 一张按距离分桶的路由表（KBucketsTable）负责组织所有已知节点，近处分辨率高、远处分辨率低；
  • 六种成对的 UDP 报文各司其职——Ping/Pong 负责验证与心跳，FindNode/Neighbors 负责逐步逼近目标，EnrRequest/EnrResponse 负责同步节点的完整档案；
  • 一套带收敛保证的查找流程，让节点能从少量 bootstrap 种子出发，像涟漪一样一圈圈扩散，最终稳定地找到离目标最近的一批节点。

理解了这三层，也就理解了以太坊网络中一个陌生节点是如何从"一无所知"走向"广结善缘"的。
