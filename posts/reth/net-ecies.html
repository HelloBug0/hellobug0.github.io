背景：什么是 ECIES

ECIES = Elliptic Curve Integrated Encryption Scheme（椭圆曲线集成加密方案）。它是 reth 中 RLPx 传输层加密的基础：节点间的 TCP 连接先用它完成 Auth → Ack 加密握手，再进入逐帧加密的通信阶段。

1. 椭圆曲线 secp256k1 数学基础

1.1 曲线参数

椭圆曲线方程：y² = x³ + 7 (mod p)，即 a = 0, b = 7。

若 x = 1，则 y² = 8 (mod p)。y 的含义：y 的平方除以 p，余数是 8。x = 1 对应曲线上的两个点，并且关于 x 轴对称。

1.2 曲线点的性质与私钥

  • p 是一个素数，n 是一个素数。
  • 将生成元 G 不断进行点加法，获得的新点都在曲线上（闭合性）。
  • 自加 n+1 次获得的点和自加 1 次获得的点相同；自加 n 次获得无穷远点，无穷远点也是曲线上的点。即曲线上的所有点构成一个素数阶循环群。
  • 为了产生不重复的私钥，私钥长度是 256 位，取值范围 [1, n-1]；在此范围内不同私钥对应不同公钥。
  • 曲线上所有点的个数 / n = 余因子。通过精心挑选参数 b 和 p 使得余因子 = 1；余因子为 1 避免这个循环群有小子群，防止小子群攻击（即防止私钥破解）。
  • 点加法满足交换律和结合律。设 P、Q、R 都是椭圆曲线上的点，则：
    • 交换律：P + Q = Q + P
    • 结合律：(P + Q) + R = P + (Q + R)

1.3 生成元的作用

生成一个随机私钥 a 之后，将生成元进行点加法 a 次，即可获得公钥 A。公钥是曲线上的一个点，包含 x 坐标和 y 坐标，即公钥是 64 字节。记为：A = a * G。

1.4 交换律与 ECDH

假设：

  • 用户 1 拥有私钥 a 和公钥 A，即 A = a * G
  • 用户 2 拥有私钥 b 和公钥 B，即 B = b * G

则：a * B = b * A，即 a * (b * G) = b * (a * G)，满足交换律和结合律。这就是 ECDH 密钥协商的数学基础——双方各自算出同一个共享点。

2. ECIESStream 代码结构解析

2.1 最小约束边界原则

impl<Io> ECIESStream<Io>
where
    Io: AsyncRead + AsyncWrite + Unpin,
{ /* connect / connect_with_timeout / connect_without_timeout / incoming */ }

impl<Io> ECIESStream<Io> {
    /* set_backpressure_boundary —— 无 trait 约束 */
}

按照最小约束边界组织代码的原则：即使 Io 不满足 AsyncRead + AsyncWrite + Unpin 这三个 trait，也可以调用下面那个无约束 impl 中实现的函数（set_backpressure_boundary）。

注意：在 stream.rs 文件中，从使用能力的角度来说，ECIESStream 实现的 connect、connect_with_timeout 等函数才是其对外提供的能力；单纯调用 set_backpressure_boundary 函数是没有意义的。也就是说，实际使用时 Io 必须满足上述三个约束，而代码中根据不同的约束分别实现 impl<Io> ECIESStream，更多是一种按照最小约束边界组织代码的严谨写法。

2.2 struct ECIESStream 与 Framed

pub struct ECIESStream<Io> {
    #[pin]
    stream: Framed<Io, ECIESCodec>,
    remote_id: PeerId,
}
  • Io 是一种泛型，和 T 含义相同；这里用 Io 是为了进一步说明这个泛型需要满足 Input/Output 特征。
  • Framed 是一个结构体，包含两个泛型（定义为 T 和 U），这里 T 是 Io，U 是 ECIESCodec。官方文档

1）是如何想到使用 Framed 结构体的？
Framed 用来将无边界的字节流转换为有边界的消息/帧。当你想要将字节流转换为消息帧的时候就可以使用 Framed 结构体。Framed 做的事情：对从 Io 处收到的字节流进行切包（粘包）、组包（半包）获得消息帧；将需要发送的包的内容发送到 Io 处。

2）如何使用 Framed<T, U> 结构体？
根据源码中 Framed 的实现可以知道：

  • T 需要满足 AsyncRead、AsyncWrite trait
  • U 需要满足 Decoder、Encoder trait
  • Framed 结构体已经实现了 Stream、Sink trait

在 codec.rs 中可以看到 ECIESCodec 实现了 Decoder、Encoder trait。

3）为什么 ECIESStream 需要实现 Stream、Sink trait？
为了 ECIESStream 对象可以直接调用 send、next 函数发送和接收消息，而且消息类型是 IngressECIESValue::Message，而不是握手用的 auth 和 ack 消息。并且在其实现 Stream、Sink trait 时，使用的是 stream.poll_next 以及 stream.start_send，所以 Message 消息会按照 ECIESCodec 结构体实现的编解码函数进行编解码。

2.3 为什么需要 Pin

本质上是因为 ECIESStream 需要实现 Stream、Sink trait，而这两个 trait 中的函数签名要求第一个参数是 self: Pin<&mut Self>，并且 Framed 类型要求 pin。所以看到 stream 字段使用了 #[pin]，结构体整体使用了 #[pin_project::pin_project]。

2.4 为什么 Io 需要 Unpin

impl<Io> Stream for ECIESStream<Io>
where
    Io: AsyncRead + Unpin,
{ /* ... */ }

impl<Io> Sink<Bytes> for ECIESStream<Io>
where
    Io: AsyncWrite + Unpin,
{ /* ... */ }

和 impl<Io> ECIESStream<Io> where Io: AsyncRead + AsyncWrite + Unpin 保持一致，只是为了显式说明 Io 类型是 Unpin 的。

2.5 握手完成的时机

服务端代码：

let listener = TcpListener::bind("127.0.0.1:0").await.unwrap();
let (incoming, _) = listener.accept().await.unwrap();
let mut stream = ECIESStream::incoming(incoming, server_key).await.unwrap();

incoming 函数返回 stream 之后，握手已经完成；后续通过 stream 对象调用 .send 和 .next 函数等都是具体的消息帧，而不是握手消息。

客户端代码：

let outgoing = TcpStream::connect(addr).await.unwrap();
let mut client_stream =
    ECIESStream::connect(outgoing, client_key, server_id).await.unwrap();

上述函数调用结束之后，握手已经完成。

3. RLPx 握手流程

本部分分三层：交互时序、报文字节布局、密钥派生。时序图只写“动作”，字节与密钥细节下沉到表格。

3.1 第一层：交互时序

真实线上握手只有 Auth → Ack 两条消息。algorithm.rs 单元测试 communicate 里出现的“第三条 ack”只是把 create_ack/read_ack 在两个方向各跑一遍做覆盖测试，并非协议流程。

客户端 (发起方)
  │ 生成 RLPx 临时密钥对 + nonce
  │ create_auth_unencrypted()
  │   S = ecdh_x(服务端长期公钥, 客户端长期私钥)
  │   sig = 用 RLPx 临时私钥对 (S ⊕ nonce) 的可恢复签名
  │   RLP[sig‖rec_id, PeerId, nonce, ver=4] + 随机填充 100~300 字节
  │ encrypt_message() —— ECIES 信封
  │   新生成一个一次性信封临时密钥
  ▼
  ═══ Auth = [len(2) ‖ 信封公钥(65) ‖ iv(16) ‖ 密文 ‖ tag(32)] ═══►
  │
服务端 (应答方)
  │ read_auth()
  │   ① 用自己长期私钥 + 信封公钥派生 kE/kM，验 tag 后解密
  │   ② 解 RLP 得 sig、PeerId、nonce
  │      （此刻才得知客户端身份——PeerId 在 Auth 里）
  │   ③ recover_ecdsa 恢复客户端 RLPx 临时公钥
  │   ④ ephemeral_shared_secret =
  │        ecdh_x(客户端临时公钥, 服务端临时私钥)
  │ create_ack_unencrypted()
  │   RLP[服务端 RLPx 临时公钥, nonce, ver] —— 无填充、无签名
  │ write_ack() → setup_frame(incoming=true)
  ▼
  ═══ Ack = [len(2) ‖ 信封公钥(65) ‖ iv(16) ‖ 密文 ‖ tag(32)] ◄═══
  │
客户端 (发起方)
  │ read_ack()
  │   ① 信封解密
  │   ② 读出服务端临时公钥 + nonce
  │   ③ ephemeral_shared_secret =
  │        ecdh_x(服务端临时公钥, 客户端临时私钥)
  │   ④ setup_frame(incoming=false)
  ▼
握手结束，进入 Header/Body 帧加密阶段
  （egress_aes / ingress_aes / egress_mac / ingress_mac）

握手一来一回的根本原因：Diffie-Hellman 需要双方互换 RLPx 临时公钥，才能各自算出同一个 ephemeral_shared_secret（与 TCP 三次握手的目的完全不同）。

3.2 第二层：报文字节布局

三层封装关系（Auth 为例）

层内容对应函数
封装一 (OUT1)RLP 明文：sig(64)+rec_id(1)、PeerId(64)、nonce(32)、version(1)，再随机填充 100~300 字节 0create_auth_unencrypted()
信封加密[65 信封公钥][16 IV][密文][32 tag]（对 OUT1 做 ECIES）encrypt_message()

关键点：2 字节长度在最前面，是包裹整个信封的外壳；其值 = 信封总长（65+16+密文+32）。这 2 字节不只是长度前缀，还作为 auth_data 参与 HMAC tag 计算，把长度字段绑进完整性校验，防止被篡改。

内层 RLP 载荷

报文RLP 字段长度处理
Authsig(64) + rec_id(1)、发起方 PeerId(64)、nonce(32)、version(1)之后随机填充 100~300 个 0（防长度指纹）

Auth 与 Ack 的不对称设计：Auth 内层用可恢复签名，接收方靠 rec_id + 签名恢复发起方临时公钥（省去显式传 64 字节公钥）；Ack 内层不签名，直接明文编码应答方临时公钥——因为应答方的身份与新鲜性已由外层 ECIES 信封（用发起方长期公钥加密）证明。

3.3 第三层：密钥派生（对应 setup_frame）

密钥派生公式用途
S（长期共享点）ecdh_x(对方长期公钥, 自己长期私钥)仅用于构造 Auth 签名摘要 S ⊕ nonce
ephemeral_shared_secretecdh_x(对方RLPx临时公钥, 自己RLPx临时私钥)会话根秘密
h_noncekeccak256(发起方nonce ‖ 应答方nonce)顺序固定，保证双方算出同值
shared_secretkeccak256(ephemeral_shared_secret ‖ h_nonce)中间量
aes_secretkeccak256(ephemeral_shared_secret ‖ shared_secret)egress/ingress AES-256-CTR，同一把钥匙、零 IV
mac_secretkeccak256(ephemeral_shared_secret ‖ aes_secret)派生两个 MAC 的种子
ingress_mac 种子MAC(mac_secret ⊕ 自己的nonce ‖ remote_init_msg)校验对方发来帧的 tag
egress_mac 种子MAC(mac_secret ⊕ 对方的nonce ‖ init_msg)生成自己发出帧的 tag

两处容易看错的细节

  1. egress_aes 与 ingress_aes 是同一把 aes_secret、IV 都为全零，只是两个独立的 Ctr64BE<Aes256> 实例各自维护计数器状态（收发方向 keystream 不互相干扰）。真正“内容不同”的是两个 MAC 的种子：各自异或的 nonce 相反、吞入的 init 消息方向相反。
  2. setup_frame 的 incoming 参数用于调换 nonce 顺序：incoming=true（服务端）用 [自己nonce, 对方nonce]，incoming=false（客户端）用 [对方nonce, 自己nonce]，从而保证双方算出的 h_nonce 一致（始终是发起方 nonce 在前）。

结语

net/ecies 模块的核心可以浓缩为三句话：

  1. 数学基础：secp256k1 上素数阶循环群的点加法交换律，支撑了 ECDH——双方用各自的临时私钥与对方的临时公钥算出同一个共享点；
  2. 代码组织：ECIESStream 把“完成握手”封装成 connect / incoming 两个异步构造函数，内部用 Framed 把字节流切成消息帧，返回后调用方直接 send / next 业务消息；
  3. 协议细节：Auth → Ack 两条报文完成身份证明、临时公钥交换与四把会话密钥的派生，长度前缀作为 HMAC 的 auth_data 绑进完整性校验。
